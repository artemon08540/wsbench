# wsbench – інструмент для порівняння методів збору даних із вебсайтів

**Тема:** «Порівняльний аналіз методів автоматизованого збору даних із динамічних веб-ресурсів».

Це вимірювальний інструмент: він однаково запускає чотири методи збору (М1 HTTP+HTML, М2 внутрішній
API, М3 headless-браузер, М4 гібрид) на тих самих сторінках і для кожного прогону записує рядок із
показниками в `runs.csv`.

> [!CAUTION]
> ### Що зроблено.
>
> **Коротко: програма завершена, основний експеримент проведено, результати готові для розділу 3.**
>
> 1. **Вибірка.** Відібрано 22 сторінки каталогів з 10 інтернет-магазинів (Україна, Польща, Франція,
>    Фінляндія). Для кожної перевірено тип сторінки: 11 SSR (товари одразу в HTML), 6 SPA (товари
>    малює JavaScript), 5 гібридних (частина товарів довантажується кнопкою).
> 2. **Еталон.** Для всіх 22 сторінок вручну підготовлено еталонні списки товарів (36–48 товарів на
>    сторінку, назва і ціна). З ними порівнюється результат кожного методу (recall, precision, F1).
> 3. **Метод М2 (внутрішній API).** Пошук JSON-API виконано автоматично на всіх сторінках. Придатний
>    API знайдено на 3 сторінках (power.fi). На SSR і гібридних сторінках каталожного API немає за
>    природою. На verkkokauppa.com API знайдено, але він повертає інший список товарів, ніж бачить
>    відвідувач (6 із 48 збігів; перевірено трьома способами), тому М2 там визнано незастосовним.
> 4. **Основний експеримент.** 22 сторінки × 4 методи × 5 повторів = **440 прогонів**, усі виконано
>    без збоїв програми (1 відмова сайту – HTTP 429, обмеження частоти запитів).
> 5. **Виправлено підрахунок підсумкових таблиць.** Незастосовні прогони М2 більше не потрапляють у
>    медіани; додано колонку «охоплення» (на скількох сторінках метод працює) і таблицю за типом сторінки.
> 6. **Зручність запуску.** Усі кроки доступні з меню `start.bat` без командного рядка.
>
> **Головні результати:**
> - **М1** (звичайний HTTP-запит) – швидкий і легкий, але повний лише на SSR: на гібридних 50 %, на SPA 0 %.
> - **М2** (API) – найшвидший (~0,3 с), але застосовний лише на 3 з 22 сторінок.
> - **М3** (браузер) – завжди 100 %, але в 3–8 разів повільніший і потребує в 4–6 разів більше пам'яті.
> - **М4** (адаптивний, запропонований) – на SSR коштує як М1, на SPA і гібридних дає 100 % як М3.
>   Тобто він поєднує переваги обох підходів, що й було метою.
>
> **Що лишилося:** згенерувати статистичний звіт (пункт 3 меню) і написати текст розділу 3.

## Крок 0. Перевірити, що все працює – демо

```powershell
python -m wsbench demo
```

Команда піднімає локальний демо-магазин із трьох сторінок (SSR, SPA з нескінченним скролом, гібрид),
проганяє всі чотири методи по 2 рази і друкує таблицю. Приклад результату:

| сторінка | М1 recall | М2 recall | М3 recall | М4 recall | час М1 | час М3 | RAM М1 | RAM М3 |
|---|---|---|---|---|---|---|---|---|
| SSR | 100 % | не застосовний | 100 % | 100 % (браузер не запускався) | ~50 мс | ~1,1 с | ~93 МБ | ~545 МБ |
| SPA | **0 %** | 100 % | 100 % | 100 % (перейшов на М3) | ~50 мс | ~5,4 с | ~93 МБ | ~575 МБ |
| гібрид | 33 % | 67 % | 100 % | 100 % | ~50 мс | ~1,1 с | ~93 МБ | ~552 МБ |

Сторінки демо-сайту штучні, тому ці числа не є результатами дослідження. Вони показують, що інструмент
коректно розрізняє SSR- і SPA-сторінки.

## Крок 1. Відібрати кандидатів і описати сторінки у `config/sites.yaml`

Попередній відбір без налаштування селекторів: `python -m wsbench discover --list config/candidates.txt`.
Для кожної адреси команда визначає доступність, дозвіл robots.txt і орієнтовний тип рендерингу, а також
пропонує селектори картки й назви. Результат – `results/discover/discover.csv`.

Для відібраних сторінок у `config/sites.yaml` задаються адреса, селектори картки, назви та ціни, тип
пагінації й очікувана кількість товарів (опис полів – у коментарях файлу). Остаточний тип рендерингу
визначається командою `check-site`.

## Крок 2. Перевірити сайти: robots.txt, тип рендерингу, endpoint для М2

```powershell
python -m wsbench check-site --sample config/sites.yaml
```

Для кожної сторінки команда покаже:
- чи дозволяє `robots.txt` обхід;
- скільки карток у сирому HTML і скільки після рендерингу, а за цим співвідношенням тип: <20 % – SPA, 20–80 % – гібрид, ≥80 % – SSR;
- JSON-запити, які робить сама сторінка і в яких є назва першого товару. Це готові кандидати для М2.

Результат зберігається в `results/checks/checks.json` і **`results/checks/sample.xlsx`** (таблиця вибірки з п. 7.1).
Якщо `card_selector` написано неправильно, обидва лічильники будуть 0. Тоді виправте селектор.

### Налаштування М2: `find-api`

```powershell
python -m wsbench find-api --sample config/sites_main.yaml
```

Команда відкриває сторінку в браузері, записує всі JSON-відповіді на фонові запити й шукає в них список
об'єктів, назви в якому збігаються з назвами товарів на сторінці. Так визначаються адреса запиту,
`items_path`, `name_field` і `price_field`. Потім запит повторюється без браузера й без cookie (так, як
його виконує М2), і перевіряється `robots.txt` для адреси API. Статуси:
`found` – endpoint придатний; `partial` – у JSON лише частина товарів (віджет, реклама);
`replay_failed` – працює лише в браузері; `replay_mismatch` – без браузера API повертає інший
набір товарів, ніж бачить відвідувач (М2 не застосовний); `robots_disallow` – заборонено
robots.txt; `not_found` – дані приходять у HTML, М2 не застосовний. Готові блоки `api:` –
у `results/find_api/api_found.yaml`.

## Крок 3. Пілот: М1 vs М3, 3 повтори

```powershell
python -m wsbench pilot --sample config/sites.yaml --methods M1,M3 --repeats 3
```

Для 5 сторінок це 5 × 2 методи × 3 повтори = 30 прогонів, кожен із часом, пам'яттю, CPU і трафіком.
Таблиця медіан пишеться в `results/pilot/summary_by_page.csv`. Колонка `t_cv_%` – коефіцієнт варіації
часу, за ним обґрунтовується кількість повторів. Поки немає еталону, `recall` порожній, а `n_found`
показує кількість знайдених товарів.

Для сторінок із відомим endpoint для М2 у `sites.yaml` додається блок `api:`, після чого запуск виконується з `--methods M1,M2,M3,M4`.

Корисні прапорці: `--pages site1_laptops` (лише одна сторінка), `--headed` (бачити вікно браузера).

**Зведені таблиці.** Медіани рахуються в два кроки: спочатку за повторами на сторінці, потім за сторінками.
Прогони зі статусом `not_applicable` не входять у жодну медіану. Колонка «охоплення» показує, на скількох

на SSR він працює як М1, на SPA і гібридних – як М3.

далі `python -m wsbench analyze --runs results/synthetic`. Ці числа вигадані й призначені лише для перевірки аналізу.

### Ваги AHP
`config/ahp.json` – матриця попарних порівнянь груп критеріїв К1/К2/К3 за шкалою Сааті (експертні судження
дослідника). Програма обчислює ваги, λmax, CI і CR та попереджає, якщо CR ≥ 0,1.

### Важливі параметри аналізу
- `--na-tests exclude|zero` – як у критеріях Фрідмана/Вілкоксона враховувати сторінки, де метод незастосовний
  (М2 без API): `exclude` – лише сторінки, де працюють усі методи; `zero` – повнота такого методу = 0.
- `--na-mcda zero|exclude` – те саме для вибору методу. За замовчуванням `zero`: обмежена застосовність
  методу враховується як його недолік.
- Пороги практичної значущості – `src/wsbench/analytics/metrics.py`, `PRACTICAL_THRESHOLDS` (фіксуються до аналізу).

## Кнопка «Показати ще» (гібридні сторінки)

Якщо для сторінки в YAML задано `load_more_selector` і `load_more_clicks`, метод М3 натискає кнопку
довантаження задану кількість разів і після кожного натискання чекає появи нових карток. М1 таких дій
не виконує, тому бачить лише першу порцію товарів. Основна вибірка – `config/sites_main.yaml`.

## Методичні рішення

- **М1 і М3 вилучають дані однією функцією** (`extract_from_html`). Методи відрізняються лише тим,
  як отримано HTML. Так порівняння коректне: різниця не залежить від того, що два парсери написано по-різному.
- **М3 запускає новий процес браузера на кожен прогін**, щоб ізолювати стан. Час запуску пишеться окремо
  (`browser_launch_ms`), тож у розділі 3 час М3 можна показати і з ним, і без нього.
- **Пам'ять** – пікова RSS процесу Python разом з усіма дочірніми процесами. Базове значення до
  прогону теж пишеться (`ram_baseline_mb`).
- **Трафік М3** вимірюється через CDP (`Network.loadingFinished.encodedDataLength`), тобто це байти «на дроті».
  Для М1/М2 це `num_bytes_downloaded` з httpx, теж стиснені байти. Отже, одиниця однакова.
- **М2 без endpoint** пишеться в журнал як `not_applicable`. Спосіб врахування таких сторінок у критерії
  Фрідмана (виключення чи recall = 0) фіксується в `journal/journal.md` до аналізу.
- **Поріг М4** за замовчуванням 0,8; аналіз чутливості до порогу (0,6/0,7/0,8/0,9) – прапорець `--threshold`.
